## 核心方向

三个独立的扩展方向，均建在 v0.1 数据模型之上（新增表/字段，不修改已有数据）：

### 1. 多词义体系

一个单词可以拥有多个独立词义，每个词义拥有独立的字段结构。

**数据层方案：**
```sql
CREATE TABLE senses (
  id TEXT PRIMARY KEY,
  word_id TEXT NOT NULL REFERENCES words(id) ON DELETE CASCADE,
  lemma TEXT NOT NULL,
  display_order INTEGER NOT NULL DEFAULT 0,
  created_at INTEGER NOT NULL
);
-- field_values 加可选 sense_id 外键
ALTER TABLE field_values ADD COLUMN sense_id TEXT REFERENCES senses(id);
```

**v0.1 迁移：** 为每个已有 word 创建一条默认 sense，现有 field_values 视同属于默认 sense。

**不影响 v0.1 已有行为：** 默认为"单词义模式"，用户不进入多词义 UI 时和 v0.1 行为完全一致。

---

### 2. 字段层级

字段值之间可以存在父子关系，例如"词义 → 中文释义 → 例句"。

**数据层方案：**
```sql
ALTER TABLE field_values ADD COLUMN parent_id TEXT REFERENCES field_values(id) ON DELETE CASCADE;
```

**视觉示意：**
```
implement (动词)
  ├── 中文释义: "实施；执行"
  │     └── 例句: "We implemented the new system."
  ├── 词性: verb
  └── 近义词: carry out, execute
```

**不影响 v0.1：** `parent_id = NULL` 的 field_values 完全等同于 v0.1 的扁平模式。

---

### 3. 展示控制 & 自定义字段

**展示控制：** 全局设置 + 单词级覆盖
```sql
CREATE TABLE display_settings (
  field_id TEXT PRIMARY KEY REFERENCES field_definitions(id),
  visible INTEGER NOT NULL DEFAULT 1,
  display_order INTEGER NOT NULL
);
CREATE TABLE word_display_overrides (
  word_id TEXT NOT NULL REFERENCES words(id),
  field_id TEXT NOT NULL REFERENCES field_definitions(id),
  visible INTEGER,
  PRIMARY KEY (word_id, field_id)
);
```

**自定义字段：** 放开 `field_definitions` 的写入权限（当前已有表结构支持，只需加 UI）

**不影响 v0.1：** 纯新增表和 UI，零改动 v0.1 数据逻辑。

---

## Service Layer 承接关系

v0.1.1 引入的 Service Layer 为 v0.2 提供承载：
- `wordService.ts` → 扩展为支持多词义
- `fieldService.ts` → 扩展为支持层级关系
- `searchService.ts` → 扩展为可搜索 senses 和层级字段

不再将业务逻辑塞入 UI 组件。

## 已知待讨论问题

（以下问题留到开始 v0.2 planning 时讨论）

1. **多词义 vs 层级字段的 UI 交互：** 是先选词义再编辑字段，还是在字段编辑器中管理词义？
2. **v0.2 的版本顺序：** 三个方向是并行做还是排期先后？建议顺序：多词义 → 层级字段 → 展示控制
3. **自定义字段的 UI：** 新建字段时需要一个"字段类型"选择器（text / multiline / select?）
4. **与专业领域（v0.4）的关系：** 专业领域是多词义的一种特例，还是独立维度？
